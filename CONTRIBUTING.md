# Contributing to VCES

Contributions should make the Standard clearer, safer, more practical, and easier to adopt across technology stacks.

## Before proposing a change

- Read `VIBE-CODING-STANDARD.md` and relevant adoption docs.
- Search for existing rules and templates before adding duplicates.
- Explain the problem, evidence, and intended audience.
- Prefer reusable principles over tool-specific prescriptions.
- Identify compatibility, security, and migration implications.

## Change categories

- **Standard:** normative requirements or interpretation.
- **Template:** reusable project document.
- **Documentation:** adoption or operational guidance.
- **Maintenance:** Markdown links, wording, consistency, and repository hygiene.

## Pull request requirements

Include the problem, motivation, proposed change, impacted adopters, risks, review performed, and version/changelog impact. Keep changes focused and avoid mixing unrelated policy updates.

## Manual review

- Check changed Markdown links and references.
- Confirm that examples are clearly optional and technology-appropriate.
- Confirm that supporting skills and templates do not conflict with the canonical Standard.
- Review the complete diff and changelog entry.
- State what was reviewed and what remains unverified.

No scripts, CI workflows, or automated validation are required to contribute to this documentation repository.

## Review principles

Universal rules remain technology-agnostic; mandatory requirements are clear and applicable; exceptions are explicit; examples are not universal prescriptions; substantive review matters more than a green status indicator.

## Versioning

Follow `docs/RELEASE-PROCESS.md`. Normative changes require a changelog entry and version decision.
